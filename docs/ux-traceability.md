# StaySync UX traceability

This document links visible StaySync interface features to the ISO 25010 evaluation areas selected for this project. It describes the current repository state, including incomplete routes. Component presence alone is not treated as evidence that a complete workflow exists. Update this map as later sections are implemented and assessed.

## Interaction capability

| Sub-characteristic | What it means here | UI features that satisfy it | Where to see it (page/component) |
|---|---|---|---|
| Appropriateness Recognizability | Users immediately understand what the system is for and what each screen does | The landing page describes GilMars stays and links to stay browsing and availability. Page titles, descriptions and breadcrumbs identify the current task. Booking instructions name the advance-booking rule, deposit and request steps. | `/` (`src/pages/Landing.tsx`); `/units`, `/units/:id`, `/availability`; `PageHeader`, `Breadcrumbs` |
| Operability and Learnability | Easy to control and learn without training | Public and guest navigation labels the main tasks. Forms keep visible labels. The availability calendar has named month controls and keyboard date navigation. Reservation requests show a three-step progress indicator. | `PublicLayout`, `GuestLayout`; auth pages; `/availability` (`DateRangePicker`); `/reservations/request/:id` (`Stepper`) |
| User Error Protection | Prevents and recovers from mistakes | Auth forms use schema validation and field-level feedback. The date picker disables dates inside the minimum advance period and booked or overlapping nights, and explains each disabled state. Reservation cancellation uses a confirmation dialog that explains the consequence. Unsaved profile, inquiry and reservation changes trigger a leave-page warning. Pending button states guard submission while requests are being sent. | `Login`, `Register`, `ForgotPassword`, `ResetPassword`; `/availability` (`DateRangePicker`); `/reservations/request/:id`; `/inquire`; `/account`; `/my-bookings` (`ConfirmDialog`); `useUnsavedChangesGuard` |
| User Engagement | Pleasant, motivating, efficient to use | A restrained green, cream and sand palette, consistent cards, stay photos, clear calls to action, and visible night and price summaries support browsing and booking. Guest list pages provide a next action when there is no content. | `/`, `/units`, `/units/:id`, `/availability`; `/my-bookings`, `/my-inquiries`; shared `Button`, `Card`, `EmptyState` |
| Inclusivity | Usable by people of varied abilities, devices and contexts | Layouts adapt to narrow screens; form controls have visible labels; focus rings and keyboard-operable controls are provided; touch controls generally use at least 44px minimum height. Calendar selection, blocked dates and availability results use descriptive labels or live announcements. Statuses use text labels alongside icons. | `src/index.css`; `Input`, `Select`, `DateRangePicker`, `StatusBadge`; `PublicLayout`, `GuestLayout` |
| User Assistance | Help, guidance and feedback when needed | A booking FAQ covers advance notice, check-out counting, deposits, date holds, cancellations, rescheduling and automatically assigned inquiry categories. A reopenable first-visit guide explains guest booking steps and gives admins role-specific orientation. Inquiry status progress, loading skeletons, validation messages, retry actions, empty states and success feedback provide contextual guidance. | `/help`; `RoleGuide` in `PublicLayout`, `GuestLayout` and `AdminLayout`; `/availability`, `/reservations/request/:id`; `/my-bookings`, `/my-inquiries` (`StatusTimeline`); `Skeleton`, `EmptyState`, `Toast`, `StatusBadge` |

## Functional suitability

| Sub-characteristic | UI evidence and current limits | Where to see it / how to assess |
|---|---|---|
| Completeness | Public stay discovery, availability checks, guest reservation requests, account access and inquiries have screens. Admin dashboard, reservations, inquiries, units, guests, keywords and booking-rules destinations currently show a preparation placeholder; their routes are not evidence of completed admin workflows. | `/units`, `/availability`, `/reservations/request/:id`, `/my-bookings`, `/my-inquiries`, `/inquire`, `/account`; placeholders in `src/App.tsx`. Assess each role's end-to-end task completion. |
| Correctness | Shared helpers format PHP amounts and stay dates. Date utilities and the picker use an exclusive check-out date and enforce advance booking in the interface. The UI presents a fixed PHP 1,500 deposit payable by GCash or bank transfer and states that dates are held only after deposit verification and admin confirmation. Verify against known date, capacity, price and booking-rule scenarios and backend responses. | `src/lib/format.ts`, `src/lib/dates.ts`; `/availability`; `/units/:id`; `/reservations/request/:id`. |
| Appropriateness | The visible public and guest tasks fit a small accommodation reservation and inquiry service. Route guards restrict guest and staff destinations by role. Several advertised admin destinations remain placeholders, limiting role task coverage. | `src/App.tsx`; `src/features/auth/ProtectedRoute.tsx`, `RoleRoute.tsx`; public and guest routes. Verify expected access and task fit with each role. |

## Performance efficiency

| Sub-characteristic | UI evidence and current limits | Measurable evidence to collect |
|---|---|---|
| Time behavior | Loading skeletons and pending button states expose waits; load errors on key guest pages offer retry or a next step. No timing result is claimed here. | Record mobile Lighthouse performance and route load timings for landing, units and admin reservations, with build, device profile and date. Admin reservations currently measures a placeholder. |
| Resource utilization | Stay images declare intrinsic dimensions and use lazy loading except for priority images. Pages and admin staff code are route-split; guest lists paginate ten records per view. The Section 7 build measurement records individual chunks and total emitted JS. Guest list API calls still fetch all records. | `StayImage`, `Avatar`; `src/App.tsx`; `/my-bookings`, `/my-inquiries`; `docs/performance.md`. Lighthouse scores, transferred image bytes and server-side pagination remain unmeasured. |
| Capacity | Guest reservation and inquiry views can render account-specific records. Shared table and pagination components exist, but current admin list destinations are placeholders; no large-list capacity claim is made. | Use a documented fictional data volume; record page size, query and render time, and repeatable response behavior on completed list screens. |

## Evidence limits and follow-up

This is a design-to-evaluation map, not a usability study, accessibility audit or ISO conformance result. It does not claim that all WCAG 2.1 AA criteria, screen-reader flows, role tasks, responsive breakpoints or performance targets have been verified. The admin business workspaces remain placeholders, and the app has no dedicated offline experience or published public phone/email; Help directs guests to the in-app inquiry form. Record test date, device/profile, build and route with any subsequent measurements so results can be repeated.
