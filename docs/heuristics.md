# Nielsen heuristic review

This review records how the current StaySync interface applies Nielsen's ten usability heuristics. It is a design review of repository-visible UI, not a moderated usability study or accessibility conformance result. Routes identified as placeholders are not counted as finished workflows.

| Heuristic | Implementation in StaySync | Where to see it | Assessment and remaining gap |
|---|---|---|---|
| 1. Visibility of system status | Data views use loading skeletons and retryable errors. Submit actions expose pending state. Successful reservation, inquiry and profile actions provide confirmation feedback. Guest reservation rows and inquiry cards pair a status badge with a plain-language explanation of what happens next; inquiry cards also show the current stage in a three-step progress display. Date selection and availability results are announced to assistive technology. | `Skeleton`, `Button`, `Toast`; `/availability` and `/units/:id`; `/my-bookings` (`MyReservations`); `/my-inquiries` (`MyInquiries`, `StatusTimeline`); `/reservations/request/:id`; `/account` | Implemented in existing guest flows. No status detail can be assessed in the admin reservation or inquiry destinations yet because those routes are placeholders. |
| 2. Match between system and the real world | Copy uses familiar terms such as stay, check-in, check-out, nights and deposit. Dates and prices use shared helpers (`Sat, Dec 12, 2026` style and `PHP 1,500`). The interface explains that check-out is exclusive, the deposit is fixed at PHP 1,500, and dates are held only after staff verify the deposit and confirm the request. | `src/lib/format.ts`; `/availability`; `/units/:id`; `/reservations/request/:id`; `/my-bookings` | Implemented in the reviewed guest booking path. Payment account details are intentionally directed to GilMars staff rather than presented as in-app payment functionality. |
| 3. User control and freedom | Reservation request steps have Back controls and preserve entered values while moving between steps. A Cancel request link remains available before submission. Inquiry composition links back to My inquiries. Account, inquiry and reservation forms warn before leaving with unsaved data. Account editing also offers Discard changes. Pending reservation cancellation requires explicit confirmation and offers Keep request. | `/reservations/request/:id`; `/inquire`; `/account`; `/my-bookings` (`ConfirmDialog`); `useUnsavedChangesGuard` | Implemented for these paths. Unsaved reservation and inquiry drafts are held in page state only; a reload does not restore them. Cancellation does not offer an undo action after confirmation. |
| 4. Consistency and standards | Shared buttons, labeled controls, cards, badges, page headers, table patterns, focus rings, typography and status language are reused across pages. The same reservation status labels and format helpers appear in guest booking views. | `src/index.css`; `src/components/ui/`; `/availability`; `/my-bookings`; `/my-inquiries` | Shared patterns are present in guest-facing areas. Admin workspaces are incomplete, so consistent task patterns across staff roles cannot yet be assessed. |
| 5. Error prevention | The calendar disables dates inside the advance-booking window and dates that are booked or would overlap booked nights. Its legend and instructions explain the dashed state; blocked dates have explanatory labels. Forms validate on blur, guest capacity is checked, request submission guards against duplicate sends, and cancellation explains its consequence before confirmation. Unsaved profile, inquiry and reservation changes receive a leave-page warning. Super-admin staff role and account access changes require confirmation. | `DateRangePicker`; auth forms; `/availability`; `/reservations/request/:id`; `/inquire`; `/my-bookings`; `/account`; `/super/accounts` (`StaffManagement`, `ConfirmDialog`); `useUnsavedChangesGuard` | Implemented for the guest booking path and available staff controls. The other high-impact admin workspaces remain placeholders. |
| 6. Recognition rather than recall | Breadcrumbs show location; guest stay browsing exposes date and guest filters; the booking stepper shows the current step; the calendar shows a legend; statuses and category names remain visible with each record. | `Breadcrumbs`, `PageHeader`, `Stepper`; `/units`; `/availability`; `/reservations/request/:id`; `/my-bookings`; `/my-inquiries` | Implemented on the public and guest routes. Admin filters, counts and corrected-category indicators await completed admin screens. |
| 7. Flexibility and efficiency of use | Calendar controls support arrow-key movement and month navigation. Availability selections can carry forward through query parameters into a reservation request. Shared table rows become labeled cards on narrow screens. | `DateRangePicker`; `/units`, `/availability`, `/reservations/request/:id`; `Table` | Some efficiency support exists. There are no dedicated expert shortcuts or bulk actions. Administrative list efficiency and pagination cannot be evaluated while those screens are placeholders. |
| 8. Aesthetic and minimalist design | Cream pages, near-white content surfaces, deep-green structure and restrained sand accents use a shared type, spacing and radius scale. Booking screens prioritize dates, prices, status and next actions. | `src/index.css`; `docs/design-system.md`; public and guest layouts and pages | The current guest-facing presentation follows the design system. Further visual consistency across admin screens depends on those screens being implemented. |
| 9. Help users recognize, diagnose and recover from errors | Field errors explain the correction; network failures keep entered reservation or inquiry details and offer retry; availability failures offer another date or stay; load failures provide a retry or next step. Auth failures use plain-language guidance. | `Input`, `Select`, `Textarea`; `/login`, `/register`; `/units`, `/availability`; `/reservations/request/:id`; `/inquire`; `/my-bookings`, `/my-inquiries` | Recovery paths are present in reviewed guest views. There is no dedicated offline page. Support and error recovery for unfinished admin workflows remains unassessed. |
| 10. Help and documentation | Booking rules, date meaning, deposit methods and confirmation conditions are shown near the relevant choices. The FAQ answers questions about advance booking, check-out, deposit, date holds, cancellation, rescheduling and inquiry categories. First-visit guides for guests, admins and super admins can be reopened after dismissal. | `/help`; `RoleGuide` in `PublicLayout`, `GuestLayout` and `AdminLayout`; `/availability`; `/reservations/request/:id`; `/inquire`; `DateRangePicker` | Implemented for documented booking steps and the available admin prototype. No public phone or email is listed in the repository, so Help directs guests to the in-app inquiry form. There is no dedicated offline experience; existing task-level network errors provide retry guidance where implemented. |

## Heuristic violations and limitations to carry forward

- The admin dashboard, reservation list, inquiry inbox, unit management, guest list, keyword tools and booking-rule screens are placeholders. Their visibility, consistency, recognition, filtering, recovery and efficiency cannot be evaluated yet.
- Reservation and inquiry drafts are not saved across reloads. The current stepper preserves values only while the reservation request page remains mounted.
- There is no dedicated offline experience. Existing network errors appear within the affected task and provide a retry or next step where implemented.
- The Help page and role onboarding cover current booking rules and prototype role capabilities. There is no dedicated offline experience.
- This review did not execute keyboard-only task completion, screen-reader review, mobile-device review or user evaluation. The documented implementation should be verified with those methods before it is reported as an evaluation result.

## Review basis

The implementation references above were checked against the current `src/pages`, `src/components` and `src/lib` source. Revisit each row after the relevant screens are complete and record any changes in evidence or limitations rather than inferring usability from component presence alone.
